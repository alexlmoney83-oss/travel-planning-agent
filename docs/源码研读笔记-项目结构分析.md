一、项目概述
------------------------------------------------------------
基于 LangChain Agent + Streamlit + MCP + RAG 的智能旅游规划系统。
核心思路：用户输入旅行需求 → Agent 自动调用多个外部工具（火车票、天气、酒店、航班、黄历等）→ 综合生成旅行规划方案。

技术栈：Python 3.11+, LangChain, Streamlit, ChromaDB, DashScope (Qwen3), DeepSeek R1, MCP 协议

架构迁移历史：从 LangGraph（图状态机模式）迁移到 LangChain ReAct Agent（思考-行动-观察循环模式），graph/ 目录是遗留代码。

三、调用关系图
------------------------------------------------------------

app.py (Streamlit UI) - 主入口
│
├── 1. configure_rag_retriever()
│     用户上传文档 → TextLoader/PyPDFLoader/CSVLoader
│     → RecursiveCharacterTextSplitter (chunk=500, overlap=100)
│     → DashScopeEmbeddings (text-embedding-v3)
│     → Chroma 向量库 → retriever
│
├── 2. pre_analyze_query(user_query, llm)
│     调用 Qwen3 提取: destination, origin, travel_days, budget, date
│     → detect_multi_destination() 判断是否多目的地
│     → 返回 scenario_type: simple | complex | multi_destination
│
├── 3. create_tools(retriever)
│     ├── 读取 tool_registry.AVAILABLE_TOOLS (10个工具定义)
│     ├── RAG 工具: create_retriever_tool(retriever)
│     ├── MCP 工具: 遍历 tool_type=="mcp" 的定义
│     │   ├── train_query → query_train_tickets() 特殊处理
│     │   │   内部调用: MCP "12306 Server" → get-stations-code-in-city
│     │   │           → get-tickets, 同时调用 Gaode Server 查自驾路线
│     │   └── 其他 MCP → make_sync_tool() 通用处理
│     │       通过 call_mcp_tool_sync() → MCPToolManager.call_tool()
│     │       → MCPServerSse (SSE 协议) → 外部服务器
│     └── R1 工具: r1_analysis → DeepSeek API (deepseek-reasoner)
│
├── 4. get_mcp_manager_sync()
│     MCPToolManager.initialize()
│     → 读取 servers_config.json
│     → 遍历 mcp_servers[] → MCPServerSse(name, params={url})
│     → 5个外部服务器:
│       · 12306 Server   - 火车票查询 (站点代码、车次、票价)
│       · Gaode Server   - 高德地图 (路线、酒店、天气、POI、地理编码)
│       · biying Server  - 必应搜索 (最新旅游资讯)
│       · bazi Server    - 八字黄历 (农历、宜忌、吉日)
│       · flight Server  - 航班查询 (条件触发: >800km)
│
├── 5. create_react_agent(llm, tools, prompt) + AgentExecutor
│     ├── simple 场景: 直接 AgentExecutor.invoke({"input": user_query})
│     └── complex/multi 场景: 增强输入(提示先调 r1_analysis)
│         → AgentExecutor.invoke({"input": enhanced_input})
│
│     ReAct 循环:
│       Thought → Action → Action Input → Observation → Thought → ...
│       直到 Final Answer
│
└── 6. Streamlit 渲染结果

七、值得注意的问题
------------------------------------------------------------

1. 【代码问题】mcp_tools.py 第 18 行有一行孤立的 "11111"，疑似调试残留。

2. 【架构问题】graph/ 目录已标记为废弃(__init__.py 导入全部注释)，

   说明废弃不彻底，旧节点代码仍在被引用。

3. 【入口混乱】存在两个 app.py:
   - 根目录 app.py (44KB): Streamlit UI，主入口
   - travel_agent/app.py (2.6KB): 命令行独立启动，备用入口
   两者没有代码复用关系，各自独立实现。

4. 【配置缺失】servers_config.json 中所有 5 个 MCP 服务器的 URL 目前
   均为空字符串，需要部署实际的 MCP Server 并填入地址后才能工作。

5. 【依赖冲突风险】mcp_tools.py 依赖 openai-agents 包的 MCPServerSse，
   但 requirements.txt 中未列出 openai-agents，仅在 setup.py 中提及。
   如果只用 pip install -r requirements.txt 会缺少该依赖。

6. 【同步/异步混用】app.py 使用 nest_asyncio + 全局 event loop (_mcp_loop)
   来在 Streamlit 同步环境中调用异步 MCP 工具，属于临时方案。


八、目录结构的构建方式分析
------------------------------------------------------------

本项目的目录结构采用 **"一次性规划骨架 + 按层逐步填充"** 的方式建立，
整个过程分为两个阶段：

【阶段一：骨架一次性铺开（Step 1.4）】

构建指南第 1.4 节要求程序员手动创建全部目录和 __init__.py 占位文件，
而不是边写代码边建目录。在写任何业务代码之前，先把完整的目录骨架建好。

程序员需要手工执行的操作：
  - mkdir 创建 aggentic_RAG/ 及其所有子目录（config/, core/, graph/, tools/, data/）
  - 每个 Python 子包创建 __init__.py 占位文件
  - 创建 data/travel_docs/ 和 data/travel_vectordb/ 数据目录
  - 这一步对应构建指南"第 1 步：环境准备"，耗时约 15 分钟

【阶段二：代码按架构分层逐步填充（Step 4 → 5 → 6 → 7）】

实际的 .py 代码文件按照依赖关系从内向外逐层实现，每一层对应构建指南的一个步骤：

  Step 4 (30min) → config/ 层         【零依赖，最底层】
    settings.py      全局配置加载器（加载 .env、定义 API Key、模型名、路径、RAG 参数）
    prompts.py       System Prompt 模板（7+ 套 Prompt，17.7KB）
    servers_config.json  MCP 服务器 SSE 端点配置

  Step 5 (2h)    → tools/ 层          【依赖 config/，读取 API Key 和配置】
    mcp_tools.py     MCP 客户端（SSE 连接管理、工具调用、重试机制）
    rag_tool.py      RAG 检索系统（ChromaDB + Embedding + 去重）
    r1_tool.py       DeepSeek R1 API 封装
    tool_registry.py 工具注册表（10 个 ToolDefinition）

  Step 6 (3h)    → graph/ + core/ 层  【依赖 tools/，节点中调用工具】
    state.py         TravelPlanState 定义（TypedDict，40+ 字段）
    nodes.py         工作流节点实现（planner、R1 strategy、ReAct 循环等）
    workflow.py      工作流图结构 + 条件边路由
    agent_executor.py  Agent 执行器（5 阶段流水线）

  Step 7 (2h)    → app.py 入口层      【依赖以上所有层】
    根目录 app.py           Streamlit UI 主入口（44KB）
    travel_agent/app.py     命令行备用入口（2.6KB）

【组织原则】

1. 分层架构（Layered Architecture）：
   app.py (UI 入口层)
     └─ core/agent_executor.py (Agent 执行层)
          └─ graph/ (工作流引擎层)
               └─ tools/ (工具集成层)
                    └─ config/ (配置基底层)

2. 模块内聚：同一目录内的文件按单一职责聚合
   - config/：3 个文件各管一摊（运行参数 / LLM 指令 / 外部服务地址）
   - tools/：4 个文件对应 4 个工具域（MCP / RAG / R1 / 注册表）
   - graph/：3 个文件对应 LangGraph 三要素（State / Nodes / Workflow）

3. 内层不依赖外层：config/ 不 import 任何项目内模块，
   tools/ 只 import config/，graph/ 只 import tools/ 和 config/，
   这种"依赖倒置"使得每一层可以独立测试。

4. 一次性创建骨架的优势：
   - 目录结构即设计文档，新人一眼看懂整体架构
   - __init__.py 预先定义好包的导出边界
   - 后续写代码时无需分心管理目录，专注业务逻辑
   - 多个开发者可并行在不同目录工作（config 和 tools 可同时开工）

【对比：如果逐个构建的差异】

如果采用"边写边建目录"的方式，可能会出现：
  - 后期文件无处安放，临时添加目录打破原有结构
  - 循环引用更容易发生（因为缺乏预先的边界划分）
  - 代码 review 难以判断文件放置是否合理

本项目的"先骨架后填充"方式，本质上是用目录结构作为架构约束，
强制开发者遵循分层设计，避免代码腐化。


九、app.py 双入口详解
------------------------------------------------------------

项目存在两个 app.py，各自独立实现，没有代码复用关系。

1. 根目录 app.py — Streamlit Web UI（主入口，~1042行）
------------------------------------------------------------

定位：面向最终用户的 Web 聊天界面。

核心职责：
  - Streamlit 页面：提供完整的聊天 UI，包括侧边栏（文档上传、系统配置、
    工具列表）、对话历史展示、输入框。
  - 文档上传 + RAG 索引：用户可上传 TXT/PDF/CSV 旅游攻略，系统自动分块
    （chunk=500, overlap=100）→ DashScopeEmbeddings 向量化 → ChromaDB 存储。
  - 预分析层：pre_analyze_query() 用 Qwen3 提取目的地/日期/预算等字段，
    detect_multi_destination() 判断简单场景 vs 多目的地/复杂场景，决定是否
    启用 DeepSeek R1 深度分析。
  - 工具构建：create_tools() 从 tool_registry.AVAILABLE_TOOLS 读取 10 个工具
    定义，动态创建 LangChain Tool 对象（RAG 检索 + 7 个 MCP 工具 + R1 分析）。
  - MCP 管理：get_mcp_manager_sync() 通过 nest_asyncio + 全局 event loop
    在同步 Streamlit 环境中管理异步 MCP 连接（12306、高德、必应、黄历、航班
    共 5 个服务器）。
  - Agent 执行：使用 create_agent()（新版 LangChain API）+ MemorySaver 做
    对话记忆，按场景分流——简单场景直接调 Qwen3，复杂/多目的地场景先强制调
    R1 再做后续工具调用。
  - 特殊处理：train_query 内部做了站点代码→车票查询的两步流程，且自动附带
    自驾路线查询；各 MCP 工具有参数映射逻辑（日期年份修正、城市名清理等）。

启动方式：streamlit run app.py


2. aggentic_RAG/travel_agent/app.py — 命令行独立入口（备用，~96行）
------------------------------------------------------------

定位：开发测试用的命令行脚本，不依赖 Streamlit。

核心职责：
  - 提供 run_travel_agent(user_query) 异步函数，手动构建 TravelPlanState
    初始状态字典（包含 destination、budget、travel_days、ReAct 循环状态等
    40+ 字段）。
  - 调用 travel_workflow.ainvoke() 走完整的 LangGraph 工作流（图状态机模式），
    recursion_limit=200。
  - 底部 main() 是硬编码的测试用例（"北京到上海3天旅游"），用 asyncio.run()
    执行。
  - 依赖的是旧架构 graph/ 目录下的 workflow.py 和 state.py，走 planner →
    R1 strategy → ReAct loop → R1 optimization → synthesizer 的 5 阶段流水线。

启动方式：python -m aggentic_RAG.travel_agent.app
